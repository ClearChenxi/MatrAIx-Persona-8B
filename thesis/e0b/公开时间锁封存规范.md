# T结果公开时间锁与E2两阶段释放规范

状态：**无需导师、保管人、独立账户或人工签名；时间锁代码已具备，真实时间表和封存尚未执行，正式T预测不得开始。** 用户决定保留E2，并在E1/E1a预测全部封存后才使用适配标签；全部E2预测封存后才评价最终标签。

## 机制与边界

使用drand League of Entropy主网Quicknet的公开随机信标和官方`tlock/tle v1.2.0`。每份密文直接绑定固定链哈希与未来轮次；对应BLS签名公开前，执行者没有可自行保存的解密私钥。链、方案、公钥、周期、工具模块版本和Go模块校验和固定在`timelock-policy.json`。

实现依据：[drand/tlock](https://github.com/drand/tlock)和[drand HTTP API](https://docs.drand.love/dev-guide/API%20Documentation/)。只允许生产Quicknet，不允许测试网。

这套机制能证明密文在指定轮次前不能依靠正常协议解密，也能避免执行者自行提前释放。它不能追溯证明封存前从未看过或复制过明文，也不能证明本机之外不存在旧副本。论文必须保留这一限制，不得把公开时间锁写成第三方对既往行为的证明。

## 六个密文对象

- `T_adaptation_labels`：328条，绑定第一阶段轮次。
- `T_final_evaluation_labels`：1,386条，绑定第二阶段轮次。
- 私有标签摘要、兑换源、交易源和原始压缩包：均绑定第二阶段轮次，因为它们可能泄露或重建最终评价结果。

完整T标签在内存中按冻结`e2_role`确定性拆分，不写拆分明文。生成密文后仍须保留至少两份经SHA-256复核的密文副本；确认副本可读后，才可在另一次明确授权下移除五项原始明文。封装程序不会自动删除任何数据。

## 时间表登记

两个UTC时间必须在E1成本和工期测定后、任何正式T预测前确定。适配轮次至少比登记时的公开最新轮次晚7天，最终轮次至少再晚7天。实际日期应留出充足余量：

1. 第一阶段日期前完成全部E1/E1a预测、质检、哈希登记、提交和推送。
2. 第二阶段日期前完成全部获批E2预算预测、质检、哈希登记、提交和推送。
3. 若任一预测冻结未在对应时间前完成，该阶段判定为治理失败；不得在标签已可解密后补做预测并冒充预注册结果。

登记命令会从Quicknet实时取得链信息和最新轮次，并把目标时间向上映射到第一个不早于目标时间的轮次：

```sh
.venv/bin/python thesis/e0b/register_timelock_schedule.py \
  2026-12-01T00:00:00Z \
  2027-01-01T00:00:00Z
```

以上日期仅为格式示例，不是已批准时间。登记后必须先提交并推送策略，不能直接封装。

## 工具与封装

本地工具从固定Go模块版本构建，不提交二进制：

```sh
.venv/bin/python thesis/e0b/install_tle.py /path/to/new-tle-directory
```

从已推送、干净的实验分支生成六个密文：

```sh
.venv/bin/python thesis/e0b/prepare_timelock.py \
  thesis/e0b/runs/e0b-20261011T033848.685233Z \
  /path/to/new-timelock-package \
  --tle /path/to/new-tle-directory/tle
```

准备程序在加密前复核完整T标签和四项源对象哈希，拒绝过去或不足7天的适配轮次；随后解析每个age密文的`tlock`接收者字段，确认链哈希和轮次确实写入密文。先运行：

```sh
.venv/bin/python thesis/e0b/verify_timelock.py package \
  thesis/e0b/runs/e0b-20261011T033848.685233Z \
  /path/to/timelock-package/timelock-seal-manifest.json
```

复制并复核至少两份密文后，再单独处理明文访问权。五项原始明文都不可读后运行：

```sh
.venv/bin/python thesis/e0b/verify_timelock.py initial \
  thesis/e0b/runs/e0b-20261011T033848.685233Z \
  /path/to/timelock-package/timelock-seal-manifest.json
```

只有输出`public_timelock_seal_verified`才允许开始正式T预测。

## 两阶段解锁

第一阶段前，E1/E1a冻结清单必须位于Git仓库中，列出全部预测文件SHA-256并绑定时间锁清单。核验器要求冻结文件与指定提交完全相同、代码提交与冻结提交都已进入远端实验分支、提交时间和冻结时间早于解锁时间。公开轮次到达后，`unlock_timelock.py adaptation ...`只解密适配标签。

第二阶段采用相同流程，但冻结清单必须覆盖E1、E1a和E2。轮次到达后才允许解密最终评价标签及其他受保护源对象。对应模板为`e1-freeze-manifest.template.json`和`e2-freeze-manifest.template.json`。

解锁命令要求阶段名、E0b运行、时间锁清单、冻结清单、包含该冻结清单的远端提交和新输出目录。例如第一阶段：

```sh
.venv/bin/python thesis/e0b/unlock_timelock.py adaptation \
  thesis/e0b/runs/e0b-20261011T033848.685233Z \
  /path/to/timelock-package/timelock-seal-manifest.json \
  /path/in/repository/e1-freeze-manifest.json \
  <freeze-commit> \
  /path/to/new-adaptation-unlock \
  --tle /path/to/tle-directory/tle
```

Git提交时间可以由提交者设置，因此它不是密码学时间戳；审计时还应保存GitHub远端提交页面或自动化运行的公开时间证据。真正阻止提前获知标签的是drand轮次和明文移除，Git记录负责证明预测版本的可追溯性。
