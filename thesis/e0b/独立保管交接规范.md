# T结果独立保管与E2两阶段释放规范

状态：**治理方案已修正，独立交接尚未执行，正式T预测不得开始。** 用户已决定保留E2，并在E1/E1a预测全部封存后才进行E2。当前仍是同一系统账户下的本地逻辑封存；本规范不能追溯证明执行者过去从未接触T结果。

## 保管范围

完整`labels_T_SEALED.csv`必须确定性拆成两个独立逻辑对象：

- `T_adaptation_labels`：328条，只能在E1/E1a全部预测封存后释放。
- `T_final_evaluation_labels`：1,386条，只能在全部获批E2预算预测也封存后用于最终评价。

只拆派生标签仍不足够。`coupon_redempt.csv`可重建主标签Y1，`transaction_data.csv`可重建辅助标签Y2，原始压缩包可以恢复全部源表；私有标签摘要也会泄露结果。因此初始交接共生成六个独立密文对象：两份标签分区、私有摘要、兑换源、交易源和原始压缩包。交接验收后，执行账户必须无法读取五项原始明文来源。

## 信任锚

保管人可以是导师、课题组管理员或执行者无法控制的独立系统账户，不需要参与模型开发。交接前必须完成以下预登记并先提交、推送：

1. 保管人姓名、角色和完整GPG公钥指纹写入`custody-policy.json`。
2. 公钥文件SHA-256写入同一策略。
3. 导师或机构通过仓库外渠道确认“姓名—角色—指纹”，其签署声明或原始确认文件的SHA-256写入策略。
4. 执行环境只能导入公钥，不得持有对应私钥。

核验器只接受策略中的预登记指纹，不读取回执自报指纹。变更保管人必须产生新的策略提交并重新进行外部确认，不能用临时回执覆盖。

## 初始交接

在交接前应先完成仍需原始交易表的人工Persona审核。`prepare_custody.py`从已提交、已推送的干净分支启动，在内存中按冻结`e2_role`拆分T标签并直接加密，不写拆分明文；其他四项源对象直接加密。程序会拒绝未登记指纹、公钥哈希不符、外部确认哈希不符或本机持有保管人私钥的情况。

保管人核对六项密文与交接清单后，用预登记密钥签署初始回执。只有保管人确认收到可解密密文后，才另行撤销执行账户对五项原始明文的访问。删除或移交明文属于不可逆操作，不由准备程序自动执行。

初始核验同时要求：交接清单正确、回执由预登记指纹签署、执行账户不持有私钥、五项原始明文均不可读。满足后状态才是`independent_custody_verified`。

## 两阶段释放

第一阶段是适配标签释放：

1. 使用D/R完成开发、稳定性试跑和总协议冻结。
2. 对适配池与最终评价池生成并封存全部E1/E1a基础及消融预测。
3. 冻结清单提交、推送并登记所有预测SHA-256。
4. 保管人核对清单并签署`adaptation`释放回执，只解密交付`T_adaptation_labels`。
5. 执行者按冻结的小预算完成E2；不得用适配结果回改E1/E1a。

第二阶段是最终评价：

1. 所有获批E2预算的最终评价预测均已封存、提交、推送并登记SHA-256。
2. 保管人签署`final_evaluation`回执。
3. 默认由保管人在隔离环境中使用冻结评价程序计算并签署结果；若确需交付逐户标签，也只能在该回执通过后进行。

因此不会出现“等E2预测完成才释放E2所需适配标签”的死锁，适配标签也不会解封最终评价标签。

## 自动核验

交接前的本地E0b核验持续检查九个登记源对象为`0444`。完成保管人预登记并提交、推送策略后，使用以下命令生成密文交接包；该程序不会自动删除或移走任何明文：

```sh
.venv/bin/python thesis/e0b/prepare_custody.py \
  thesis/e0b/runs/e0b-20261011T033848.685233Z \
  /path/to/new-custody-package \
  /path/to/external-custodian-attestation
```

保管人确认密文可解密、签署初始回执，并且执行账户已失去五项原始明文的读取能力后，使用：

```sh
.venv/bin/python thesis/e0b/verify_custody.py initial \
  thesis/e0b/runs/e0b-20261011T033848.685233Z \
  /path/to/handoff-manifest.json \
  /path/to/custody-receipt.json \
  /path/to/custody-receipt.json.asc
```

两个释放阶段使用`verify_custody.py release adaptation ...`和`verify_custody.py release final_evaluation ...`。核验器同时检查冻结清单的阶段身份、代码已提交推送声明、所需预测集以及非空SHA-256清单。

当前`custody-policy.json`中的保管人状态仍为`pending_external_registration`，没有签名回执，五项明文也仍可读，所以实际独立保管尚未闭环。
